## Known follow-up: mcp-atlassian dropped after a live field-test failure

Sprint 1 deferred live MCP-protocol verification of `mcp-atlassian` to "once the orchestrator exists and calls it Cloud-Run-to-Cloud-Run." That happened in Sprint 2 — and surfaced a real, unresolved bug in the pinned `sooperset/mcp-atlassian:0.23.1` image itself, not a config or credentials problem on our side:

- Networking was fine once `mcp-atlassian`'s ingress was opened from `internal` to `all` (Cloud Run's `ingress: internal` only accepts traffic that routes through Google's internal VPC network, and by default a Cloud Run service's outbound calls to *another* Cloud Run service's public URL do **not** count as internal, even same-project — this needs a Serverless VPC Access connector to actually work as "internal," which wasn't provisioned. Since IAM auth — `roles/run.invoker` scoped to `orchestrator@` only — still fully gated access, opening ingress didn't weaken the actual security property).
- Once reachable, the real MCP session (initialize → tools/call) worked correctly, and `mcp-atlassian` correctly routed the `jira_create_issue` tool call.
- But `mcp-atlassian` itself then failed with `401 Unauthorized` calling Atlassian's own `/rest/api/2/myself` — **with two different, independently-verified-valid API tokens** (each confirmed working via a direct `curl -u email:token` REST call, both immediately after rotating them in Secret Manager and after forcing a fresh Cloud Run revision to pick up each new secret version). This rules out a bad/expired token; the failure is inside `mcp-atlassian`'s own Jira-auth code path (its traceback shows it runs Jira calls through an SSRF-protection hook, `attach_ssrf_hook=True`, which appears to interfere with outbound Basic Auth in this environment) — a third-party image bug, not something fixable from our side without much deeper investigation.

**Resolution:** `jira/client.py` now calls the Jira Cloud REST API directly (same credentials, same Secret Manager token, Basic Auth) — proven reliable throughout this diagnosis. `mcp-atlassian` was deleted. If MCP-based tool access is ever wanted again (e.g. for a future domain-expert agent), it would need either a from-scratch re-implementation or a different pinned image version, and should be smoke-tested against real Jira auth *before* being wired into the orchestrator's critical path again.

The very first live test of the Intake Agent's real Gemini call failed with `ValueError: No API key was provided.` Investigation found neither `aiplatform.googleapis.com` (Vertex AI) nor `generativelanguage.googleapis.com` (Gemini Developer API) was enabled on the project at all — this had been silently assumed done since Sprint 1, but was never actually a completed prerequisite, and no unit test could have caught it since unit tests mock the model.

**Resolution (Vertex AI, no new secret needed — consistent with the rest of the architecture's "orchestrator's own service account" pattern):**
- Enabled `aiplatform.googleapis.com`.
- Granted `orchestrator@` → `roles/aiplatform.user`.
- Added Cloud Run env vars: `GOOGLE_GENAI_USE_VERTEXAI=TRUE`, `GOOGLE_CLOUD_PROJECT=artisan-multiagent-ai`, `GOOGLE_CLOUD_LOCATION=global`.

That last one caught a second, non-obvious bug: with `GOOGLE_CLOUD_LOCATION=us-central1` (matching every other resource in this project), Gemini calls 404'd with "Publisher model ... was not found or your project does not have access to it" — even though the model *was* visible in `client.models.list()` and the Cloud Console Model Garden page for it showed no access/enablement gate at all. Confirmed via a standalone script that `gemini-2.5-flash` worked fine on `us-central1` while `gemini-3.7-flash` only responds on Vertex AI's **`global`** location. `TECH_STACK.md`/`SYSTEM_DESIGN.md` now call this out explicitly since it's not discoverable from the Console UI.

## Known follow-up: Pub/Sub infinite-retry incident (found + fixed Sprint 2)

While field-testing the above, discovered the orchestrator had been in a continuous Pub/Sub redelivery storm since 01:47 UTC — **~95 minutes and 4,400+ failed requests** by the time it was caught — because the push subscription had no dead-letter policy and no retry-policy backoff cap configured. Two Firestore tickets were stuck permanently retrying: `ART-7` (from synthetic test issue `990006`, which never existed on GitHub — a 404 that could never resolve, retried forever) and transiently `ART-8` (issue #2 itself, before the Vertex AI fix).

**Resolution:** created dead-letter topic `artisan-github-events-dlq`, wired the required IAM (Pub/Sub service agent → `roles/pubsub.publisher` on the DLQ topic, `roles/pubsub.subscriber` on the source subscription), and set `max-delivery-attempts=5` on `artisan-github-events-push`. `ART-7`/the `990006` Firestore ticket was manually marked `manual_pickup` and the Jira ticket commented + transitioned to Done, same as the `ART-1`–`ART-6` cleanup. **This is a real gap in Phase 2.1's failure-handling story** (a non-retriable failure — like a GitHub 404 that will never resolve — must not be allowed to retry forever just because the handler raises rather than terminating gracefully); worth a proper code-level fix in Sprint 6's hardening pass, not just the infra-level mitigation done here.

## Known follow-up: Jira's real workflow has no "PR Open — Awaiting Review" status (found Sprint 3)

Firestore's own `TicketDoc.status` field still tracks `"pr_open"` exactly as `SYSTEM_DESIGN.md` §6.4 specifies — it, not Jira's coarser 4-status workflow, is the real source of truth for this state. `docs/SYSTEM_DESIGN.md` §4 and `docs/SPRINT.md` Phase 3.6 updated to reflect this. If a real "PR Open"-shaped Jira status is wanted later, it would require a Jira admin reconfiguring this project's workflow scheme (outside this repo's control, and not attempted here without being asked).

## Known follow-up: ADK's built-in `bash_tool` can't run unattended (found Sprint 3)

While designing `execution-sandbox`'s coding step, initially planned to reuse ADK's built-in `google.adk.tools.bash_tool.ExecuteBashTool` (it ships with a `BashToolPolicy` for command allowlisting/resource limits, which looked like free sandboxing). Reading its `run_async` implementation before committing to it surfaced a blocker: it unconditionally calls `tool_context.request_confirmation(...)` before every single command, with no constructor flag or policy setting to disable this — it's built for an interactive human-in-the-loop flow. In an unattended Cloud Run Job with no human present to approve, every tool call would return "this tool call requires confirmation" forever, since nothing ever confirms it.

**Resolution:** `execution-sandbox/src/artisan_execution_sandbox/coding_agent.py` uses plain Python functions (`read_file`/`write_file`/`list_directory`/`run_shell_command`/`finish`) as tools instead. ADK wraps plain callables as `FunctionTool`, which defaults `require_confirmation=False` — confirmed by reading `function_tool.py` and by a local spike script exercising the full multi-round function-calling loop (ADK's `base_llm_flow.run_async` loops `_run_one_step_async`, one LLM call per round, until the model's response contains no more function calls — confirmed this happens automatically within a single `runner.run_async()` invocation, which `intake_agent.py`'s existing usage never actually exercised since it has no tools at all). A `MAX_CODING_AGENT_TOOL_CALLS` cap (40) stops a stuck model from looping past the job's own execution timeout — tested with a fake model that always requests another tool call.

## Known follow-up: a duplicate-delivery race in the idempotency guard (found + fixed Sprint 3 close-out)

While planning Sprint 3's live end-to-end test, re-read `app.py`'s `/pubsub/push` handler and found a real bug that had been live since Sprint 2, just never triggered: the push subscription's `ackDeadlineSeconds` was `10`, but the delivery was only marked "seen" (`mark_delivery_processed`) *after* `handle_event` fully returned — for Gate 1 that's fast enough to rarely matter, but Gate 2 can run for minutes (several LLM calls plus a full Cloud Run Job execution). Pub/Sub redelivering the same message while the first attempt is still mid-flight would have hit `is_duplicate_delivery` before it was ever marked, and re-run the entire Gate 2 pipeline concurrently — a second PR, a second Jira comment, etc.

**Resolution:** idempotency is now a claim, not a flag. `gcp/firestore_client.py`'s `is_duplicate_delivery`/`mark_delivery_processed` were replaced with `claim_delivery`/`mark_delivery_completed`/`mark_delivery_failed`, following the exact transactional commit-then-decide shape already used for the `clarification_rounds`/`retry_count` caps. A `processed_deliveries/{delivery_id}` doc's `status` moves `in_progress` → `completed` (permanent dedupe) or `in_progress` → `failed` (immediately reclaimable, so Pub/Sub's own retry-on-genuine-failure still works); a stale `in_progress` claim older than `DELIVERY_CLAIM_STALE_AFTER_SECONDS` (70 min — deliberately longer than the orchestrator's 3600s/60min max request timeout, so a claim never goes stale while the underlying request could still legitimately be running) is also reclaimable, so a Cloud Run instance dying mid-request can't block that delivery forever. `app.py`'s handler now claims before calling `handle_event`, and marks failed/completed in a `try`/`except` around it, re-raising so Pub/Sub's dead-letter policy still sees genuine failures. As additional (secondary) headroom, the push subscription's `ackDeadlineSeconds` was also raised to 600 (Pub/Sub's ceiling) and the orchestrator's own Cloud Run request timeout to 3600 — neither is what actually fixes the race, but both reduce redundant redelivery traffic while Gate 2 is genuinely still working. See `docs/SYSTEM_DESIGN.md` §7/§6.4 for the updated schema description.

## Known follow-up: `orchestrator@` was missing the IAM role for Cloud Trace (found + fixed Sprint 3 close-out)

During the Sprint 3 close-out's live end-to-end test, checked the Cloud Trace API directly for the `gate: "1"`/`gate: "2"` spans Phase 2.5/3.7 claim as done — found zero traces, and orchestrator logs showing `PermissionDenied: 403 Permission 'cloudtrace.traces.patch' denied` on every span export attempt, going back at least to the start of this session's live testing. `orchestrator@`'s IAM roles (Firestore, Pub/Sub, Secret Manager, Vertex AI, Cloud Run Jobs-trigger) never included a Cloud Trace role at all — the `tracing.py`/`CloudTraceSpanExporter` code was correct, but every span had been silently dropped since Sprint 2.

**Resolution:** granted `orchestrator@` → `roles/cloudtrace.agent` (the standard role providing `cloudtrace.traces.patch`). This was **not** re-verified with a fresh live trace afterward — doing so would have meant forcing another real GitHub issue through the pipeline solely to check tracing, which wasn't worth the additional live-system noise on top of the one already run (see Milestone 5). The fix directly matches the exact permission the 403 error named, so confidence is high, but this is flagged here as fixed-not-independently-reverified rather than glossed over as fully confirmed. Worth a quick trace check the next time a ticket runs through Gate 1 or Gate 2 for any other reason.
